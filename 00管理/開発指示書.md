# Matching Reply Assistant

## Codex実装設計書

## 1. 概要

個人用のローカルWebアプリとして、マッチングアプリの会話を再現し、AIによる返信文章の作成・修正・保存を支援する。

実際のマッチングアプリとは一切連携しない。

ユーザーが実際のマッチングアプリから相手のメッセージをコピーして本アプリへ入力し、本アプリ上でAI返信を生成する。完成した文章はコピーして実際のマッチングアプリへ貼り付ける。

本アプリ内の「送信」は、外部サービスへの送信ではなく、本アプリ内のチャット履歴へ自分のメッセージとして追加する操作を意味する。

最重要目標は、

「相手のメッセージを入力 → AIに返信を作らせる → 必要なら修正 → コピー」

までを極力少ない操作で完了できること。

---

# 2. 基本方針

* ローカルWebアプリとして動作する
* PC上のブラウザからlocalhostへアクセスする
* 実際のマッチングアプリとは連携しない
* 外部APIとの通信はBackendから行う
* API KeyをFrontendへ渡さない
* プロジェクトフォルダを別PCへコピーして利用できる
* PC固有の絶対パスを使用しない
* すべてのアプリデータはプロジェクトルートを基準として保存する
* AI Providerを抽象化し、将来的にモデルを追加できるようにする
* 初期AI ProviderはCerebras
* 初期モデルはgpt-oss
* AIの「学習」は初期段階ではFine-tuningではなく、ルール・参考資料・過去のフィードバックを生成時に参照する方式とする
* 将来的なRAGやFine-tuningに利用できるよう、フィードバックデータは構造化して保存する

# 14. AI生成に利用する情報

返信生成時には、以下の情報をBackendで組み立ててAIへ渡す。

1. 絶対ルール
2. 今回の追加条件
3. 相手情報
4. 会話履歴
5. 参考資料
6. 過去のフィードバック・良い返信例

「絶対ルール」は必ず守る。

「今回の追加条件」は固定ルールに反しない範囲で強く反映する。

参考資料は判断材料として利用する。

過去のフィードバックは、ユーザーの好みを反映するために利用する。

# 15. ルール

保存場所：

knowledge/rules/

ルールとは、

「AIが返信文章を生成するときに必ず守る事項」

である。

例：

* 自然な日本語にする
* 相手の発言を無視しない
* 過度に馴れ馴れしくしない
* 不自然な褒め方をしない
* 長すぎる返信を避ける

など。

複数のTXTファイルを登録可能。

アプリ起動時に自動的に読み込む。

不要なファイルは削除可能。

---

# 16. 参考資料

保存場所：

knowledge/references/

参考資料とは、

「マッチングアプリでどう立ち回るか」

「会話をどう進めるか」

「どういう返信が良いか」

など、ユーザー自身が作成した知識資料。

ルールとは異なり、必ず守る命令ではなく、AIが判断する際の参考情報として扱う。

複数ファイルを登録可能。

アプリ起動時に自動的に読み込む。

削除可能。

---

# 17. ルールと参考資料の優先関係

AIプロンプト内で明確に区別する。

RULES：

必ず守る。

REFERENCES：

判断材料として参考にする。

参考資料がルールと矛盾する場合はルールを優先する。

# 31. API Key管理

API Keyはソースコードへ直接記述しない。

Git等の管理対象へ平文で保存しない。

ログへ出力しない。

Frontendへ返さない。

可能ならOSの安全な資格情報ストレージを使用する。

別PCへ移行した場合は、必要に応じてAPI Keyを再設定できる。

.env.exampleには、

CEREBRAS_API_KEY=

のような空のテンプレートだけ用意してよい。

# 49. Fine-tuning

初期実装ではFine-tuningを行わない。

理由：

* Provider依存が強い
* 実装・運用が複雑になる
* まずはルール＋参考資料＋フィードバックで十分な効果を検証できる
* ユーザー固有のデータを先に蓄積することが重要

将来的にFine-tuningを導入できるよう、データ構造だけは対応可能にする。

相手の名前・プロフィール・画像説明等

マッチングアプリに関する参考資料

* 最近のフィードバック
* 採用された返信
* 高評価された返信

などから適切な件数を選択して利用する。

将来的にEmbedding/RAGへ拡張する。

# 65. セキュリティ

本アプリは個人用ローカルアプリだが、最低限のセキュリティを実装する。

* API KeyをFrontendへ送らない
* API Keyをログへ出さない
* 外部サービスへ不要な情報を送らない
* 外部サービスとの通信はBackendからのみ行う
* ローカルBackendを外部ネットワークへ不用意に公開しない
* ファイルパスをユーザー入力から直接信頼して扱わない

# 68. Codex実装ルール

Codexはこの設計書を基本仕様として扱う。

実装前にプロジェクト全体を確認する。

いきなり全機能を一括実装せず、Phase単位で実装する。

各Phase完了時に動作確認する。

既存機能を壊さない。

PC固有の絶対パスを使用しない。

データ保存先はプロジェクトルート基準にする。

API Keyをソースコードへ直接記述しない。

API Keyをログへ出力しない。

Frontendから外部AI APIを直接呼び出さない。

Provider固有コードをFrontendへ記述しない。

AI Providerを抽象化する。

DB構造を変更する場合はMigration等を考慮する。

既存データを意図せず削除しない。

新機能追加時には可能な範囲でテストを追加する。

READMEおよびdocsを実装状況に合わせて更新する。

仕様が明確でない細部については、既存設計と矛盾しない最も単純な実装を選択する。

勝手に外部サービスとの連携機能を追加しない。

実際のマッチングアプリへの自動ログイン・自動送信・スクレイピング等は実装しない。

# 69. 完成形

最終的な利用フロー：

1. アプリ起動
2. 相手を選択
3. 相手の最新メッセージを確認
4. 必要なら相手メッセージを入力
5. 「今回の返信条件」を入力
6. AI返信生成
7. 生成結果を確認
8. 必要なら修正指示
9. 再生成
10. 採用
11. コピーして実際のマッチングアプリへ貼り付け
12. 本アプリでは「送信」で自分のメッセージとして履歴へ追加
13. チャット履歴を自動保存

最終的には、

「自分のルール」
+
「自分が作った参考資料」
+
「相手の情報」
+
「今までの会話」
+
「自分が過去に良いと判断した返信」
+
「今回だけの条件」

をAIが利用し、

「自分が納得できる返信を短時間で作る」

ことを目的とする。
